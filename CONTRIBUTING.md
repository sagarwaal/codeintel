# Contributing

Thanks for helping improve Project Intelligence.

## Before opening an issue

- Search existing issues to avoid duplicates.
- Include the coding agent/tool and relevant environment where possible.
- Describe the repository shape and task type that exposed the problem.
- Remove proprietary source, credentials, tokens, private data, and other sensitive details.

## Pull requests

1. Explain the problem and the proposed change.
2. Keep the core skill generally useful across repository types.
3. Prefer evidence-based, tool-agnostic instructions; put specialized guidance in references when appropriate.
4. Do not add claims that imply a test or verification ran unless it did.
5. Check Markdown formatting and links.
6. Include an example or reproduction steps for behavioral changes.
7. Avoid committing generated project knowledge, private repository data, or real source-code audit output.

## Design principles

- Be explicit about uncertainty and scope.
- Preserve user work.
- Avoid destructive actions without authorization.
- Adapt the knowledge structure to project size.
- Keep the source code as the source of truth.
- Optimize for useful future engineering work, not document volume.
